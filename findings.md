## f. The authoring findings

- Scope was not bound by the first pack. The pack that ran the rehearsal pinned the approval id and the payload hash on both seats and not the account, and could not have, since the exporter of that day exported none. An attacker-authored trace splicing account A's two seats onto account B's Execute replayed ALLOW under that pack. Nothing in the language required the pin; the pack had validated, passed 43 fixture bundles and rehearsed with every cell holding [the exhibit `test/support/campaigns/dogwood/pack/census/R1_scope_unbound_first_pack/` (the first pack `pack.dw`, sha256 `7c34dd5c9f96f320ccfe11ad1821dd74d6313e71cc8a1980bc3872a52cb1616d`, its schemas, `spliced.log`, `replay.json` reading `allow`, `determining_rules: [0]`); G-191 in `docs/internal/gaps.md`]. The deliverable's pack carries the scope on every event and pins it on both seats; the same splice denies under it [`pack/rules/00_f5_two_person_execute.dw` in the run directory; `test/support/campaigns/dogwood/pack/fixtures/_pack/spliced-seats-other-scope-deny/`]. This is a finding about authoring burden, not expressiveness.
- The horizon is a policy constant. Every window in the pack is a literal `within 24h`, tied to the plane's authority TTL by a test, not by derivation; a Dogwood window is a literal or a macro parameter, so an approval's own `expires_at` cannot be a per-event window. That is why `T1-F5-expired-explicit-001` disagrees [G-174; `trials.jsonl`].
- Closed versus half-open window at the boundary. Dogwood's `within` is closed at both ends; Requisition's deadline ends at the instant. At exactly +TTL Dogwood allows and Requisition denies (`T1-F5-expired-boundary-001`) [`trials.jsonl`; the catalogue row notes; `pack/fixtures/f5_two_person_execute/boundary-allow/`].
- A `Req::System` seat satisfies distinctness. Rule 00 types its two variables at validation only; at evaluation each binds to whatever entity the trace wrote, and there is no type test on a bound variable, so a system-actor seat and a user seat are "two distinct principals" [G-175; the reviewer's probe recorded in `docs/slices/requisition/REQ-093-dogwood-phase-2-policy-pack-and-expressiveness-census/README.md`, fix review item 10]. No driven row exercised it: both seats are users by the driver's construction.
- A per-key attempt count denies a legitimate retry. Row 6 measured it: the refused attempt at +0 is in rule 02's self-inclusive per-key count, so the retry under fresh authority at +100 is the second Execute of the key and is denied, while Requisition, whose refusals never consume the key, served it (`T1-F7-retry-after-refusal-001`) [`trials.jsonl`; the catalogue row notes]. The pack's bag carries no outcome, so it cannot express the distinction between a served effect and a refused attempt.

**The epoch.** Every instant in a trace is a pinned epoch plus the row's offset, which is what makes two runs byte-identical. v0.1.0's traces were stamped from epoch `2026-01-01T00:00:00Z` (`@t 1767225600`). The plane stamps each receipt's `occurred_at` from that same pinned clock, and the published evaluation key `evaluation_ed25519_v1` is valid from `2026-09-05T00:07:58Z`, so a v0.1.0-epoch receipt is outside the key's signing window and the public verifier refuses it, correctly. v0.2.0's traces are stamped from epoch `2026-09-06T00:00:00Z` (`@t 1788652800`), the earliest midnight inside the window; every offset, window and pre-registered verdict is relative to the epoch, so nothing but the absolute instants moved, and the row-by-row identity above is the measurement of that [`test/support/campaigns/dogwood/catalogue.ex`: `@epoch`; `traces/` of both runs]. The registry's window was not moved, no second key was added, and no receipt is stamped from the wall clock.

**What a receipt shows, and what it does not.** `receipts/<trial>.json` holds the run's receipt chain in the public verifier's envelope (`key_id`, `sequence`, `receipt_hash`, `signature`, `signed_payload`, `subject_id`) and the redacted subject event it commits to (`event_type`, `status`, `code`, `proof_hash`, `occurred_at`, `sequence`, `chain_scope`, `id`; no payload, no prompt text, no detection internals — the redaction ceiling is what the public traces already carry) [`receipts/`; `registry-used.json`: key id, public key, the HolyTrinity-Benchmark registry's repository, path, commit `d19945c5647d8e59b18bc7ec242ca39fbd2162ff` and sha256]. All 125 receipts across the 28 files are under `evaluation_ed25519_v1`. The reader's step 7 checks registry → signature → chain → `proof_hash` → the signed status and refusal code against the row in `trials.jsonl` → the row binding, and fails closed: `VERIFY DOGWOOD SIDE: PASS`, 1169 checks, 28 rows verified, with `verify_receipt.py` and `evaluation-registry.json` obtained from the HolyTrinity-Benchmark repository, not from this package [`README-verification.md`: "The three-way split"]. A receipt proves that the allow/deny and the code in `trials.jsonl` are what *this plane signed*, under a published key, hash-chained — inspectable. It does not prove the plane was right: the plane's code is not here, and whether it *should* have refused is the pre-registration's and this report's argument, not something a reader can run. `proof_hash` is opaque to the reader: its preimage carries the policy snapshot and is not shipped.
